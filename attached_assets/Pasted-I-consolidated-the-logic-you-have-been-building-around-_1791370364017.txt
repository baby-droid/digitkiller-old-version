# 3. Your 1,000 / 100 / 50 / 20 / 10 tick logic

The 1,000 ticks are the **structural baseline**, not automatically the entry trigger.

Use:

```text
1,000T = long-term structure
100T   = primary current distribution
50T    = medium confirmation
20T    = short confirmation
10T    = immediate entry trigger
```

For example:

```text
1,000T → EVEN structure
100T   → EVEN 54.2%
50T    → EVEN 56.0%
20T    → EVEN 60.0%
10T    → EVEN 70.0%
```

This is stronger than simply saying:

```text
EVEN = 70%
```

because the engine can determine whether the short-term move agrees with the larger structure.

# 5. Even / Odd engine

Calculate:

```text
Odd %  = odd digits / total × 100
Even % = even digits / total × 100
```

Then compare all windows.

### Example

```text
1000T  ODD 51.8
100T   ODD 54.1
50T    ODD 56.0
20T    ODD 60.0
10T    ODD 70.0
```

This produces:

```text
ODD FLOW
Agreement = 5/5
```

But:

```text
1000T ODD 51.8
100T  EVEN 53.2
50T   EVEN 55.0
20T   ODD 60.0
10T   EVEN 70.0
```

produces:

```text
CONFLICT
NO ENTRY
```

The engine should **never force a trade simply because the latest 10 ticks look attractive**.

# 6. Over 1 → Over 7

Your Over engine should explicitly calculate:

```text
OVER 1
OVER 2
OVER 3
OVER 4
OVER 5
OVER 6
OVER 7
```

For barrier `b`:

```text
Over(b) =
count(digit > b) / total × 100
```

So:

```text
OVER 1 = digits 2–9
OVER 2 = digits 3–9
OVER 3 = digits 4–9
...
OVER 7 = digits 8–9
```

Then score each barrier across:

```text
1000T
100T
50T
20T
10T
```

Example:

```text
OVER 2

1000T = 76.1%
100T  = 78.0%
50T   = 80.0%
20T   = 85.0%
10T   = 90.0%
```

This becomes a strong candidate **only if the shorter windows are not contradicting the structural distribution**.

Deriv's proposal API accepts a barrier for digit contracts, so the selected barrier can be passed into the actual contract proposal. ([Deriv API][2])

# 8. Entry digit logic

For digit contracts, the engine should produce:

```text
ENTRY DIGIT
```

but only when there is sufficient evidence.

For example:

```text
Market: 1HZ100V
Contract: MATCH
Entry Digit: 7
Score: 84
Runs: 3
Entry: NEXT ELIGIBLE TICK
```

The entry digit should be derived from:

```text
1000T digit structure
+
100T concentration
+
50T persistence
+
20T recurrence
+
10T latest behaviour
```

Not simply:

```text
latest digit = entry digit
```

---

# 9. Match logic

MATCH needs much stronger conditions than ODD/EVEN.

Use:

```text
target digit concentration
+
repeat count
+
same-digit recurrence
+
short-window persistence
+
absence of conflicting transition
```

Example:

```text
Digit 7

100T = 14%
50T  = 16%
20T  = 20%
10T  = 30%

Previous recurrence = 3
```

Then:

```text
MATCH 7
```

can become a candidate.

But if:

```text
10T = 30%
20T = 12%
50T = 10%
100T = 10%
```

the system should recognize that as a short-term spike and **not automatically enter**.

---

# 10. Differs logic

DIFFERS should work against the strongest repeated target.

For example:

```text
Dominant digit = 7
7 concentration = unusually high
repeated 7 pattern detected
```

The system can generate:

```text
DIFFERS 7
```

but only when the concentration is sufficiently high and the recurrence engine indicates that the target has become over-concentrated.

This is particularly important because MATCH and DIFFERS should **not simply be opposites selected from one percentage**.

# 11. Rise / Fall engine

Use actual tick-to-tick price movement.

```text
Rise =
number of upward transitions
/
all directional transitions

Fall =
number of downward transitions
/
all directional transitions
```

Then compare:

```text
50T
20T
10T
```

Example:

```text
50T RISE = 58%
20T RISE = 62%
10T RISE = 70%
```

→ RISE candidate.

But:

```text
50T RISE = 60%
20T FALL = 55%
10T RISE = 71%
```

→ conflict → WAIT.

# 12. Only Up / Only Down

Treat these as a separate **directional persistence engine**, not simply another name for Rise/Fall.

Require:

```text
direction persistence
+
short-window confirmation
+
low reversal frequency
+
sufficient directional edge
```

Example:

```text
UP persistence
50T = 63%
20T = 68%
10T = 72%

reversal rate = low
```

Then:

```text
ONLY UP
```

becomes eligible.

# 15. Entropy / concentration filter

If the distribution is approximately:

```text

1 = 10%
2 = 10%
```


```text

3 = 14%
```

creates a stronger candidate environment.

# 18. Run-count engine: 1–10

The signal page should not always say 10 runs.

Use:

```text
Score 74–77 → 1 run
Score 78–81 → 2 runs
Score 82–84 → 3 runs
Score 85–87 → 4 runs
Score 88–89 → 5 runs
Score 90–91 → 6 runs
Score 92–93 → 7 runs
Score 94–95 → 8 runs
Score 96–97 → 9 runs
Score 98–99 → 10 runs
```

But apply additional guards:

```text
IF conflict = true
    runs = 0

IF entropy too high
    runs = 0

IF data < 1000 ticks
    no ENTRY NOW

IF short-window reversal
    reduce runs

IF previous losses exceed limit
    runs = 0

IF signal becomes invalid
    stop
```

So **score is not probability**. It is a setup-quality score.


Messages can be:

```text
SIGNAL

ACK
```

The AppDeploy realtime architecture supports persistent WebSocket connections, connection IDs, entity subscriptions and server-side updates, which is what I used for this pairing design.

# 25. Deriv execution pipeline

The actual authenticated trading layer should use:

```text
active_symbols
      ↓
ticks_history
      ↓
ticks subscription
      ↓
contracts_for
      ↓
proposal
      ↓
buy
      ↓
proposal_open_contract
      ↓

```

Deriv's current API provides `ticks_history` for historical ticks, `ticks` for realtime ticks, `contracts_for` for available contracts on a symbol, `proposal` for pricing, `buy` for purchasing, and `proposal_open_contract` for monitoring an open contract. ([Deriv API][1])

## 27. Important accuracy rule

I would **not** design this as a system that claims it can predict Deriv's next tick "accurately" with certainty. The correct engineering target is:

> **maximize signal quality through multi-window confirmation, reject ambiguous conditions, measure live performance, and never convert a setup score into a guaranteed win probability.**

Your existing app already has the right foundation for this because it has the live WebSocket, 1,000-tick history, digit distribution, parity, barriers, rise/fall, recurrence and market ranking. The new **Mark Syn Trader Signal** layer turns those separate analyses into one coordinated decision and bot-routing system.

I also preserved the distinction between **analysis** and **authenticated real-money execution**: the public Deriv feed can supply the market data, but the actual `buy` operation requires the user's authenticated trading connection. ([Deriv API][3])
